# Code plan: make the site match Lifetime Access Agreement v3.2

The agreement now makes promises and sets limits that the code does not yet enforce or show.
This plan lists each change, the file it touches, and how to check it. Order is by risk.

## 1. Acceptance at checkout (agreement s.10) — DONE

Built: `public/agreement/index.html` (agreement page), a required checkbox in the checkout for
Lifetime plans and Lifetime add-ons only (`public/about-us/index.html`), and server enforcement
in `netlify/functions/subscribe.mjs` (rejects without `agreementVersion: '3.2'`, stores
`{ version, acceptedAt }` on the order and on the issued code as `rec.agreement`). The agreement
page is generated by the same script as the Word file, so regenerate both when the text changes
and bump `AGREEMENT_VERSION` in both places.

Original notes:

Today the pricing-page checkout (`public/about-us/index.html`, submit handler around the
`/api/subscribe` call) only asks for name and email. Nothing shows the agreement or records
that the buyer accepted it.

- Add a required checkbox before "Generate PayMongo QR": "I have read the Lifetime Access
  Agreement and the FAQ" with links to the agreement and `/faq/`.
- Publish the v3.2 agreement as a PDF under `public/` (for example `public/agreement/`) so the
  link works. Keep it indexable-neutral (no private data).
- Send `accepted: true` and `agreementVersion: '3.2'` in the `/api/subscribe` body. In
  `netlify/functions/subscribe.mjs`, reject the request without it and store
  `{ agreementVersion, acceptedAt }` on the order, then copy it to the issued code record.
- Show the same checkbox for the two add-on buttons and the Event Pass? Add-ons yes (they are
  Lifetime purchases); Event Pass and monthly plans keep their own terms.
- Check: submit without the box (blocked), with it (QR appears), order record has the fields.

## 2. Device slot rotation limit (agreement s.3) — DONE

Built: `SWAP_LIMIT = 3` per calendar month (Manila time) with helpers in `netlify/lib/core.mjs`.
Only codes with `rec.agreement` (bought under v3.x) are limited. Enforced in `portal.mjs`
(`device.remove`), `license.mjs` (Offline App `deactivate`); the stale-slot takeover in
`redeem.mjs` is counted but never blocked. Admin "Reset device swaps" button
(`resetswaps` in `admin.mjs`) clears the count; Admin "unbind" is never counted. My Events shows
"x of 3 device swaps used this month".

Original notes:

`netlify/functions/portal.mjs` `device.remove` frees a slot with no limit, `license.mjs`
`deactivate` does the same for the Offline App, and `redeem.mjs` frees a stale slot after
`STALE_DEVICE_DAYS` (7) when all slots are taken. One code can be passed around many people.

- Add `rec.freed = [timestamps]` on the code record. Record an entry on `device.remove`,
  `deactivate`, and a stale-slot takeover.
- Before freeing, count entries in the current calendar month. At 3, return a friendly error:
  "You have freed 3 devices this month. Message us if a device was lost, stolen or broken."
- Admin override: in `public/admin.html` add a "Reset device swaps" action backed by a new
  case in `netlify/functions/admin.mjs` that clears `rec.freed`.
- Decide whether a stale-slot takeover counts. Recommendation: yes, but never block it, only
  log it, because it protects an honest renter whose iPad lost its saved data.
- Check: remove devices 1 to 3 (ok), 4th blocked, admin reset allows it again.

## UPDATE (later): email is now fully locked, and device alerts

The 2-changes-per-year rule below was replaced: once a Lifetime code has an email, the renter can
never change or clear it in My Events (`emailLocked` in `core.mjs`, enforced in `portal.mjs`); only
Admin can (Change email, or Transfer code). A code with no email can still add its first one.
My Events shows the email read-only. Also new: `alertDeviceFreed` (`core.mjs`) emails the owner
when a Lifetime renter removes a device (My Events), deactivates the Offline App, or has an
unused device replaced automatically. It needs the Netlify environment variable `ALERT_EMAIL`
(the address to alert; nothing is sent if it is unset), only tells you, and never blocks or
suspends anything. Test: `node scripts/test-email-lock-and-alerts.mjs`.

## 3. Transfer and email changes (agreement s.3 and s.7) — DONE (email part superseded, see above)

Built: helpers in `netlify/lib/core.mjs` (`EMAIL_CHANGE_LIMIT = 2` per rolling 365 days;
the first email set on a code is free; clearing and re-adding counts). `portal.mjs`
`account.save` blocks the third change with a message to contact us and logs each change in
`rec.emailHistory`. `admin.mjs`: `setemail` is unlimited but logged, and a new `transfer` action
moves the code once (needs a new, unused email; a second transfer asks for an override). Admin
has a "Transfer code" button. Limits apply only to codes with `rec.agreement`.
Not built: a "Transferred" badge in the Admin list, and an agreement line stating the 2-per-year
limit (s.3 currently only says the email stays with the same business).

Original notes:

`portal.mjs` `account.save` lets the renter change the email on a lifetime code at any time.
That email is also the "Forgot your code?" recovery address, so changing it is a silent
transfer.

- Keep name changes free. For email changes on a lifetime code, keep a history array
  `rec.emailHistory = [{ from, to, at }]`.
- Limit to 2 email changes per year. Beyond that, return "Message us to change the email".
- Add `case 'transfer'` to `admin.mjs`: sets the new email, writes `rec.transferredAt`, refuses a
  second transfer unless the admin ticks "override". Show a "Transferred" badge in admin.
- Check: change email twice (ok), third blocked; admin transfer works once, second warns.

## 4. Immediate suspend for sharing or leaks (agreement s.7) — DONE

Built: Admin "Disable" now asks for a reason (leak, sharing, abuse, security, other), stored as
`revokeReason` and `revokedAt` and shown in the code's details. New "Replace code" button
(`replacecode` in `admin.mjs`, logic in `netlify/lib/replace.mjs`): makes a new code with the same
settings, events list, booth setups, uploaded frames/logos/sounds, themes and lock PIN, disables
the old one (`replacedBy`), and moves the email over. A replaced code cannot be restored.
Not carried over: guest-payment accounts (PayMongo key and vouchers are sealed to the old code), so
the renter reconnects them with a new payments PIN, and print counters. Tested with in-memory
stores only; try it on a test code against the real store before relying on it.

Original notes:

`admin.mjs` already has `revoke`, so the technical side exists. Missing is a reason and a
replacement path.

- Add a `revokeReason` field ("leak", "sharing", "abuse", "security") when revoking, shown in
  admin and stored on the record.
- Add a "Replace code" action (new code, same events, settings and devices) for the leaked-code
  case, then revoke the old one. Check whether `sendcode` can email the new code.
- Check: revoke with reason, old code shows "disabled" on the booth, replacement keeps events.

## 5. Final Offline App for a shutdown (agreement s.6) — DONE (server and Admin)

Built: Admin card "Shutdown mode (end of service)" with a typed `END SERVICE` confirmation
(`shutdownget` / `shutdownset` in `admin.mjs`, flag in `meta` via `getShutdown` / `setShutdown`
in `core.mjs`). While ON: (1) every Lifetime code may use the Offline App even if it was an
Online-only plan, and (2) `licenceFor()` in `netlify/lib/license.mjs` signs Lifetime licences with
`chk` and `hard` set to the year 2100 and `feat.final = true`, so the existing desktop and Android
licence checks never ask for a check-in again. No app change was needed for that; the booth
screen in the Windows/Mac app now says "final version" instead of "works offline until". Test:
`node scripts/test-shutdown-mode.mjs` (includes the real desktop licence code, 10 years ahead).
Not done: shipping a separate "final" installer with the update checker switched off, and
confirming the Android settings screen shows the final-version note (its gating works either way).
Practical steps on the day: switch it ON, tell renters to open the app online once (or send an
Offline activation key), keep the download pages and installers somewhere that does not need the
site, and give 90 days' notice first.

Original notes:

`netlify/lib/license.mjs` signs licences with `chk` (check in by) and `hard` (stop date),
`CHECK_DAYS = 75`, `GRACE_DAYS = 30`. A "final version" needs a licence that never asks to
check in.

- Add a `sunset` setting (in the settings store used by `getSettings()`). When it is on,
  `licenceFor()` sets `chk` and `hard` far in the future (for example 50 years) and marks
  `feat.final = true`.
- Desktop (`desktop/`) and Android (`android/`): when `final` is true, skip the check-in loop
  and the "go online" warning.
- Admin: a "Start shutdown mode" switch with a confirm, and a banner text for the booth.
- Build and host a final release (`public/app/`) tagged as final, with no auto-update.
- Check: with the switch on, an activated laptop and an Android tablet keep working with no
  network for 120 days of simulated time.

## 8. Data deletion on request (agreement s.4) — DONE (needs the Apps Script redeployed)

Built: Admin "Delete event photos" button (`events` and `deleteevent` in `admin.mjs`). It signs a
2-minute, single-use "trash" ticket (`trashDriveFolder` in `core.mjs`) and the Apps Script relay
(`apps-script/upload.gs`, new `verifyTrashTicket_` and `trashEventFolder_`) moves that one event
folder to the Drive Trash, only if it is inside the root folder. The event is marked
`deletedAt`, My Events then shows it as deleted, and a later session on the same event starts a
fresh folder (`events.mjs`). Test: `node scripts/test-delete-event-photos.mjs` (fake relay that
checks tickets like the real one). BEFORE USE: paste the new `apps-script/upload.gs` into the
Google Apps Script project and Deploy → Manage deployments → New version; until then Admin shows
a clear message and changes nothing. Note: Google keeps trashed files about 30 days, the same as
the 7-day cleanup does today.

Original notes:

- Check whether `netlify/functions/admin.mjs` can delete one event's online photos before the
  7 days. If not, add a "Delete event photos" action using the same code path the nightly
  cleanup uses.

## Suggested order

1. Acceptance at checkout (1), because every new sale depends on it.
2. Supported devices block (6) and wording (7), which are text only.
3. Device and email limits (2, 3), then the admin tools (4, 8).
4. Shutdown mode (5), which is the largest change and needs desktop and Android builds.

## Out of scope for this plan

Existing buyers who signed earlier versions keep their old terms. Do not apply the new
limits (device swaps, email changes) to their codes unless they agree in writing. Mark codes
with `agreementVersion` so the limits only apply to codes issued under 3.x.
